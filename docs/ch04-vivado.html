CHAPTER 04

Vivado 幕后与一键化

你已经跳了五遍五步舞——这次我们溜进后台,看乐队在演奏什么。呼吸周,不写新电路。

1 · 钩子:三个你答不上来的家常问题

  2. 那 4MB 的 lab01.bin(4,045,520 字节,就躺在 labs/lab01-blink/ 里)——一个 24 位计数器而已,凭什么 4MB?里面装的是什么?

3 · 五步舞的幕后:每一步在造什么

先把口径钉死:五步舞就是 build.tcl 里那五步——建工程 → 加源 → 综合 → 实现 → 比特流;GUI 里对应五个按钮:Create Project / Add Sources / Run Synthesis / Run Implementation / Generate Bitstream。把它们竖着看一遍,每步的"产出物"才是重点:

① 建工程 Project Setup —— create_project:立一张户口页——工程目录 + 芯片型号 xc7z020clg400-2(速度等级 -2 抄错,后面全白搭)
↓
② 加源 Add Sources —— add_files:把手写物登记进户口——设计源 .v、约束 .xdc、指定顶层模块。到这步为止,一切还只是"清单"
↓
③ 综合 Synthesis —— Verilog(RTL)翻译成 网表(Netlist):一张"零件+连线"的图纸,零件是 LUT、FF、进位链这些芯片里真实存在的东西
↓
④ 实现 Implementation —— 网表住进真实硅片:零件领户口、挑坐标、连线走金属(内部分三幕,下面展开)。这步做完,你的电路在物理上已经"长好"了
↓
⑤ 比特流 Bitstream —— 把几百万个开关的状态打包成一个文件:.bit。烧写 = 把这份"开关总账"灌进芯片
内幕 · 实现(Implementation)一步,后台分三幕

④ 在 GUI 里只占一个 Run Implementation 按钮,Tcl 里只占一条 launch_runs impl_1,但它内部连演三幕:

  • 映射(Mapping) —— 图纸上的零件逐一领到户口:这个加法器拆成 24 个 LUT、那排寄存器落成 24 个 FF……结果记进利用率(Utilization)报告;
  • 布局(Placement) —— 给每个零件挑物理坐标(塞进哪一格可配置逻辑块(Configurable Logic Block, CLB))。零件放得好,线就短;
  • 布线(Routing) —— 把图纸上的每根连线,变成芯片里真实的金属线段:一路闭合可编程开关。

所以"映射/布局/布线"不是五步舞里的三步,而是第四步"实现"的内幕三幕——你在报告里看到的三者痕迹,都躺在 impl_1 这一个 run 的目录里。

知识 · LUT 到底是怎么"万能"的

ch00 说过 LUT(查找表)是"可编程门",现在兑现原理:一个 6 输入 LUT 就是一张64 格的真值表——任意 6 输入的逻辑函数,无非是 64 种输入组合各自对应什么输出。把这张表写进 LUT 的配置存储,它就"变成"了你要的任何门。所以综合器不造门,它只是把你的代码翻译成一张张真值表 + 一堆"连线开关"。所谓 FPGA 可编程,编的就是这些表和开关;所谓比特流,装的就是它们的内容。一个 7z020 有 53,200 个 LUT,每个 64 格——这就是 4MB 比特流的主要去处。

每一步都留了证据:两份必会打开的报告

打开工程里的 impl_1(或直接看 build.tcl 跑完的目录),学会看两份:

报告在哪看看什么
利用率报告Open Implemented Design → Reports → Utilization(或 Tcl:report_utilization)LUT / FF / BRAM 用量和占比——你的电路在芯片里占了多大地方
时序摘要Open Implemented Design → Reports → Timing Summary(report_timing_summary)WNS——下一节专门讲

4 · WNS:ch03 那堂课的全芯片回执

ch03 讲了每个触发器都有建立/保持时间要求。同步设计里,任意两个触发器 A→B 之间隔着一段组合逻辑,Vivado 布局布线完精确知道这段路径的延迟,然后替全芯片每一对触发器做一遍算术:A 的时钟沿到 B 的时钟沿之间有 20ns 可用,路径实际要耗多少 ns——这就是静态时序分析(Static Timing Analysis, STA):"静态"指它不跑仿真,纯查表算延迟,所以又快又全,一条路径都不漏。

每条路径的富余量叫时序裕量(Slack):slack = 可用时间 − 实际需要时间。全芯片最差的那条路径的 slack,就是最差负裕量(Worst Negative Slack, WNS)。判据一句话:WNS ≥ 0,全芯片每条路径的建立时间都被满足;WNS < 0,有路径来不及。这正是 build.tcl 最后一行打印的那个数——你跳五遍五步舞,Vivado 就替你做了五遍全芯片踩脚检查。

步骤 · 亲手读一次(5 分钟)
  1. 随便打开你哪个工程(lab01/lab02 都行),Flow Navigator → Open Implemented Design;
  2. Reports → Timing Summary,摘要表第一行就是 WNS(TNS 是违反路径的总量,为 0 即全过);
  3. 找到 WNS 那行点开,能看到最差路径从哪个触发器到哪个触发器、各段耗了几 ns——课程里的设计 WNS 大概率是几十 ns 的正数(离极限很远),但你要会读。
知识 · 万一 WNS 真是负的,两句话自救

① 降频:把 xdc 里 create_clock 的周期改大(可用时间变多)——最常用,课程内永远够用;② 减逻辑级数:把长链条组合逻辑中间插一排寄存器(流水线),让每拍干的事变少。记住方向即可,真做时序收敛是毕业路线图里的话题。

5 · GUI 只是 Tcl 的皮(今天最值钱的心智模型)

Vivado 的母语是 Tcl(Tool Command Language,发音近 "tickle")——一种 1980 年代诞生的工具胶水语言。你在 GUI 里的每一次点击,Vivado 都把它翻译成一条 Tcl 去执行。不信?当场验证:

步骤 · 5 分钟对照实验(杀手锏演示)
  1. 打开任一工程,把 Tcl Console(Window → Tcl Console)拖到顺手的位置;
  2. 在 GUI 里做下面表格左列的任何一个动作,眼睛盯着右列——每次点击,Console 实时打印出等价命令。
你在 GUI 里点……Tcl Console 打印的等价命令
Add Sources 加文件add_files ...
设顶层模块set_property top xxx [current_fileset]
Run Synthesislaunch_runs synth_1
Run Implementationlaunch_runs impl_1
Open Implemented Designopen_run impl_1
Generate Bitstreamlaunch_runs impl_1 -to_step write_bitstream
打开 Utilization 报告report_utilization
Program Device 烧板program_hw_devices ...

两个推论,对你这个命令行重度用户是纯爽点:

  • build.tcl 不是什么黑客手段,它就是 GUI 流程本身——你只是绕过皮,直接说母语。
  • 你的每次点击都有存档:Vivado 每个会话都把执行过的 Tcl 逐条写进当前目录的 vivado*.jou(日志回放文件,Journal)——想不起"刚才那个操作叫什么",翻 .jou,把它抄进你的脚本。学会读 .jou,等于 GUI 里的一切操作都可复制。

补上最后一块:program.tcl,烧写也一键

五步舞有 build.tcl,但烧板你还在点 GUI。补上(已放进 labs/lab01-blink/program.tcl):

# Lab 01 一键烧写脚本 —— GUI 里点 Program Device 的全过程,就这七行
open_hw_manager
connect_hw_server              ;# 连本机 hw_server(默认 localhost:3121)
open_hw_target                 ;# 探测板上的 JTAG 链

set dev [lindex [get_hw_devices xc7z020*] 0]
set_property PROGRAM.FILE [glob ./lab01.runs/impl_1/*.bit] $dev
program_hw_devices $dev        ;# 烧!
用法:cd labs/lab01-blink && vivado -mode batch -source program.tcl
警告 · JTAG 是"易失"装载,而且主人只有一个

① JTAG 烧写断电即失(比特流只写在配置存储里,不进 Flash),按 RST 也会清掉——正常,不是坏了。② 如果烧写连不上/卡住:你跑过 OpenOCD,它和 Vivado 的 hw_server 抢同一个 JTAG 口,先 pkill -x openocd(两个 JTAG 主人的互杀问题,附录 A 有专条)。

知识 · 顺手包个 Makefile(CLI 党自取,GUI 党可跳)
build:
	vivado -mode batch -source build.tcl
flash:
	vivado -mode batch -source program.tcl
clean:
	rm -rf lab01 *.jou *.log *.str
.PHONY: build flash clean

从此 make build 出比特流、make flash 上板、make clean 还你干净目录。

6 · 比特流解剖:4MB 里装的是什么

拿 lab01 开刀。一个 .bit 文件从前往后三段:

段内容怎么亲眼看到
① 明文头部设计名、器件型号、生成时间等管理信息(ASCII)xxd lab01.bit | head,右边直接能读出字母
② 同步字FF FF FF AA 99 55 66——配置协议的"开场白",告诉芯片"管理信息到此为止,后面是正片"xxd 里搜一眼;或跑 bit2bin.py,它会打印偏移
③ 配置帧一个又一个配置帧(Configuration Frame):固定长度的数据块,每帧负责芯片某一小片区域里所有 LUT 真值表、FF 配置、布线开关的状态。约 4MB 几乎全是它就是头两段后面那一大坨

那 labs/lab01-blink/lab01.bin 和 .bit 什么关系?——它是给 ch09 的:你移植的 Debian 里,FPGA Manager 从 Linux 侧装载 FPGA,走的是 处理器配置访问端口(Processor Configuration Access Port, PCAP),而不是 JTAG;内核的 zynq-fpga 驱动要求喂给它"从同步字开始、每个 32 位字做了字节序交换"的裸数据——也就是 .bin。转换脚本早就写好了(labs/bit2bin.py,20 行,注释里链着内核驱动源码):

cd labs/lab01-blink
python3 ../bit2bin.py lab01.runs/impl_1/led_blink.bit lab01.bin
# 输出示意(字节数以你这次构建的 .bit 为准):
# OK: lab01.bin (4045520 字节, 同步字 @文件偏移 0x??)

用 xxd 验一眼字节序交换(这是本仓库里 lab01.bin 的真实前 16 字节):

$ xxd lab01.bin | head -1
00000000: ffff ffff 6655 99aa 0000 0020 0120 0230

看第 5~8 字节:.bit 里本该是 aa 99 55 66,这里却是 66 55 99 aa——正是"每个 32 位字首尾反转"的效果(前 4 个 FF 不含顺序信息,看不出来)。同时注意 .bin 从同步字开始,没有 .bit 的明文头部:所以 .bin 比 .bit 小一点点,小的那截就是头部。ch09 装载成功的那天,你会再见到这个文件。

7 · 工程卫生:git 只收藏你亲手写的东西

Vivado 的 .runs/.cache 每次构建都变,几万个小文件 + 大日志,jq 进 git 就是灾难(仓库膨胀、diff 噪音、clone 变慢)。原则一句话:凡是能由命令重新生成的,都不进 git;进 git 的只有"人写的":源码 .v、约束 .xdc、脚本 .tcl、README。模板已放在 labs/lab01-blink/.gitignore,搬走即用:

# --- 脚本流(build.tcl)生成的工程目录 ---
lab01/
# --- GUI 工程库的内部目录(若用 .xpr 工程)---
*.runs/
*.cache/
*.hw/
*.ip_user_files/
*.sim/
# --- 会话日志与回放 ---
*.jou
*.log
*.str
.Xil/
# --- 比特流默认不进 git(存档用 release/tag)---
*.bit

从此 git status 永远干净:改了哪个 .v、动了哪行 tcl,一眼见底。以后每个 Lab 的 README 里都有一行"资源账本"(见下),配合这份干净,任何一台新机器 git clone + make build 就能完整复现你的工程——这才是工程师的仓库。

9 · 常见坑

坑现象解法
把 .runs/.cache 提交进 git仓库迅速膨胀到 GB 级,clone 半小时上节 .gitignore;只留 .v/.xdc/.tcl/README
只提交 .xpr 工程文件别人(或换了目录的你)打不开——.xpr 引用绝对路径工程用 build.tcl 现建,源文件才是本体
.bit 进 git每次构建一个 4MB 二进制,diff 全是噪音忽略;要存档发 release
脚本里没 wait_on_run 就去取 .bit拿到旧文件或报"找不到"build.tcl 已示范:launch 后必 wait
烧写连不上connect/open_hw_target 卡住或报错pkill -x openocd(JTAG 互杀,附录 A);确认板卡上电
断电后电路没了,以为烧坏重新上电 LED 不闪JTAG 装载本就易失;重新 program 即可(驻留要写 Flash,本课程走 ch09 的 Linux 装载)

10 · 小结与自测
